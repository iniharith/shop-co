# Shop-Co private admin monitor

Run this as one independent, always-on Node 20+ service, separate from the Shop-Co backend. Run `npm ci` in this directory. Only one process may poll a given Telegram bot token. Create a **new** bot through BotFather; do not reuse the customer bot. Never commit secrets. A Dockerfile is included; set its build context to this directory.

Set these environment variables in the hosting provider's secret settings:

- `ADMIN_BOT_TOKEN`: new bot token.
- `ADMIN_TELEGRAM_USER_ID`: numeric Telegram user ID permitted to issue commands.
- `ADMIN_TELEGRAM_CHAT_ID`: numeric private chat ID for alerts. Start a private chat with the bot first; retrieve IDs securely via Telegram's `getUpdates` API without sharing the token. Do not use a group.
- `ADMIN_REPORT_MONGO_URI`: MongoDB URI for a read-only user with access only to `auditlogs` and `tasks` in the `shop-co` database.
- `ADMIN_REPORT_ACTOR_ID`: HARITH's Shop-Co user ID.
- `ADMIN_REPORT_DB`: optional database name, defaults to `shop-co`.
- `MONITOR_URLS`: comma-separated HTTPS endpoints. Set actual production URLs explicitly; include admin, storefront, and backend readiness endpoint.
- `SENTRY_ORG_SLUG` and `SENTRY_READ_TOKEN`: optional Sentry organization slug and a read-only token with access to its issue list. The monitor polls `sentry.io` for the 100 most recently updated unresolved issues every five minutes. It takes a baseline at startup, then alerts on new issue IDs; existing issues, regressions of already-seen IDs, resolved issues, events beyond the first 100, and issues created while the monitor is offline may not produce alerts. No stack traces or event payloads are sent.
- `SHOPCO_BOT_EMAIL` and `SHOPCO_BOT_PASSWORD`: optional dedicated Shop-Co staff account for authenticated task changes. The bot signs in through the normal API and keeps access/refresh tokens in memory only. Restrict this account's role and store credentials in the service secret settings. The owner-only `/move TASK_ID STATUS` and `/update TASK_ID title|description|dueDate VALUE` commands use the task's current version and report conflicts. These commands are not enabled unless the account is configured.
- `BOT_STATE_PATH`: required for task edits and AWB commands; use a path on a persistent, writable volume. Telegram update IDs are stored before command processing to avoid replay after a bot restart. A crash between checkpoint and execution may lose a command; check task/station status before retrying. Run a single bot replica and avoid overlapping deployments.
- `MODEL_API_URL` and `MODEL_NAME`: optional Ollama-compatible chat server and model. Remote endpoints must use HTTPS; do not expose an unauthenticated inference service publicly. `MODEL_API_TOKEN` optionally supplies its bearer token. If unset, ordinary text messages receive a setup notice. Current chat tool access is read-only (task search and website status); changes use explicit bot commands. Chat context is limited to six exchanges in memory and is lost on restart.
- `MODEL_BRIDGE_SECRET`: optional secret of at least 32 characters, configured identically on the Railway bot and the local `model-worker.js`. The bot listens on Railway's `PORT`; give the workstation its HTTPS `MODEL_BRIDGE_URL`. The worker connects outward and calls Ollama at `127.0.0.1:11434`; do not open the Ollama port to the internet. Run one worker. The service must be reachable over HTTPS and the secret is equivalent to access to the model queue; never paste it into chat. Configure `MODEL_NAME` on the bot. Without a connected worker, chat reports an error rather than inventing an answer.
- `PRODUCTION_STATION_ID`, `PRODUCTION_STATION_DEVICE_KEY`: optional, scoped pairing credentials for an approved Production Station. `/awb TASK_ID` obtains a task QR through the signed-in Shop-Co API, then queues it through the existing paired-device interface. `/awbstatus JOB_ID` reports the station result. The station must be online with automatic AWB printing enabled and its AWB printer set to Windows default. The current station pairs one device at a time, so pairing the bot may replace a paired phone; use a dedicated station or extend pairing before setup.
- `IMAGE_INDEX_PATH`: optional image-index JSON path on persistent storage. Grant the read-only database account `find` access to `fileuploads` as well as `tasks`, then run `npm run index-images` using that account. The indexer reads supported S3/Cloudinary image URLs and stores file IDs, task IDs, filenames, hashes and version hashes, not image contents. A full initial run can take a long time. Send the bot an image to find visually similar copies; text recognition requires a vision-capable model. Search is approximate, can miss or misidentify artwork, and must be checked by the user.

For a long initial index, set `IMAGE_INDEX_LIMIT` to a positive batch size. The result's `nextAfter` is the last processed file ID when more records remain; set `IMAGE_INDEX_AFTER` to that value for the next batch, using the same index file. Repeat until `nextAfter` is null. Intermediate progress reports include `lastId`; after an interruption resume from an earlier saved ID if necessary. A full run from the start revisits changed files. Run only one indexer at a time for a given file, and keep the index on storage shared with the bot.

Start with `npm start` in this directory. The process checks every five minutes and alerts on changes. `/status` checks immediately; `/task QUERY` searches task titles, order IDs and customer usernames; `/uploads` and `/uploads YYYY-MM-DD` list distinct tasks with recorded file-add audit events, in Malaysia time. This is activity, not proof of completed work; tasks deleted from the database cannot be titled. The monitor's own hosting and Telegram must be available for alerts; use an independent uptime service to monitor the monitor. Restart resets the prior status.

On the Windows workstation, after the bridge has an HTTPS URL and a secret, run `model-worker-configure.ps1` interactively in PowerShell as the Windows user who will run the worker. It prompts for the secret without echoing it, saves it encrypted to that user's Windows profile, installs a hidden startup shortcut, and copies the worker into the user's local application data. Node.js and the local Ollama service must also be available when the user signs in. Starting the shortcut immediately is separate from creating it. This setup does not create or expose a Railway endpoint; configure that independently and keep the secret private.

WhatsApp is not configured here. Business-initiated alerts generally need a configured WhatsApp Business Platform account and approved templates; never reuse a customer-facing webhook without authenticated routing and access controls.

Sentry alerts depend on Sentry being enabled and capturing errors in each deployed application; a healthy homepage does not prove every feature works. Add targeted checks and Sentry alert rules for important workflows, and monitor the monitor independently. This service cannot detect every bug or issue.

Image similarity uses perceptual hashes, so it primarily finds visually similar copies rather than concepts or semantically related designs. Vision model OCR is probabilistic; verify extracted text. Neither the end-to-end image search nor Telegram AWB printing has been validated on production. AWB status distinguishes a request or spool submission from confirmed physical output. Pairing and station routes in this checkout may not yet exist on the deployed backend; verify before configuration.

## Telegram as the Shop-Co control point

Ordinary chat can retrieve website status, task search, HARITH completed-design work reports, separate upload reports and Production queue previews. Reports use Malaysia dates and alphabetically sorted uploaded-file tasks. The assistant can prepare task updates, AWB jobs, or a Production batch. Each chat action returns an exact summary and a one-use /confirm CODE; /cancel discards it. Proposals expire after ten minutes or a restart, and a newer proposal replaces the old one. Production confirms the queue has not changed before submitting. Task updates retain optimistic concurrency protection.

Examples: “Show HARITH uploads for 2026-11-05”, “Find kakasenior2”, “Check my websites”, and “Download today's Production to Today, print drafts four per A4 and move downloaded tasks to Print AWB”. Folder names currently allow letters, digits, underscores and hyphens under the workstation's configured download root. The bot cannot execute arbitrary Windows commands or change arbitrary website settings. Chat actions need persistent BOT_STATE_PATH, authenticated Shop-Co credentials, and approved station credentials for downloads and printing.

This is a separate AI assistant integrated with Shop-Co and the Windows station. It does not automatically share the desktop Codex conversation. Local-model chat requires the PC/model worker online. Monitoring and reports run independently on Railway. No system can guarantee detection of every application bug.

## Faster daily reports and Codex PC control

/tasks yesterday, or normal text such as “what tasks did I do yesterday”, lists distinct tasks HARITH moved to DONE DESIGN on that Malaysia date, including earlier-created tasks and all current statuses. Repeated completions of the same task count once. Explicit questions about tasks created on a date use the separate creation-date report. Work reports state completion-date semantics and annotate tasks currently in Trash. /uploads remains the separate HARITH file-upload activity report. Common dated task questions bypass AI inference for speed. Chat proposals accept YES or CANCEL; confirmation codes remain supported.

With TELEGRAM_PC_ENABLED=true, ordinary chat not handled by a direct report/command is sent to the installed, signed-in Codex app server on the Windows workstation. /pc REQUEST explicitly selects the PC agent, and /pcstop requests interruption. It uses a separate persistent Codex conversation and the existing account's configured model; it does not mirror this desktop chat. The worker settings file contains codexExecutable and codexCwd; codex-pc.js must be installed next to model-worker.js. A Windows user-session mutex prevents duplicate workers at startup.

The agent retains workspace-write sandboxing and on-request approval routed to the owner. Command and file-change approvals appear as Telegram buttons; unknown approval, permission-grant and MCP elicitation types fail closed and may require the desktop client. Approval summaries are limited to 4000 characters. PC control is limited by available tools, the signed-in Windows session, and OS permissions; graphical app control is not guaranteed. Never claim a UI click, file operation or physical print succeeded without observing it.

A dynamic Shop-Co tool lets Codex query live tasks, all-task date reports, HARITH upload reports and status, and prepare task/printing actions without reading passwords or tokens. These operations are authenticated by the existing outbound bridge and scoped to an active PC job. One PC task runs at a time; its final result returns asynchronously so Telegram can still accept approvals, reports and cancellation. Restart/timeout invalidates queued approvals and causes the worker to interrupt the stale job on its next state check. Interrupted side effects may already have happened: check results before retrying.

On this Windows build the built-in shell runner incorrectly turns its working directory into a file URL. The separate windows dynamic tool provides read-only computer info and directory metadata, plus PowerShell execution only after the owner approves the exact command and directory in Telegram. Approved Windows commands run as the signed-in Windows account outside the Codex sandbox. No such command is auto-approved. Worker secrets are removed from the environment passed to Codex and command children. Commands have a two-minute deadline and cancellation requests terminate their process tree; already-completed side effects cannot be rolled back automatically.

## Continuous Windows availability

The worker supervisor runs indefinitely, restarts Node five seconds after an exit, and restarts a process tree that stops updating its local heartbeat for six minutes. The scheduled watchdog starts at Windows sign-in and checks every minute. It uses the interactive Windows account, a standard System32 working directory, no saved Windows password, and an installation directory accessible to that account. Install with install-worker-watchdog.ps1 -InstallRoot PATH. A local mutex prevents overlapping supervisors.

The supervisor finds the current Codex executable after desktop updates; the PC client also resolves a removed version directory before launching. Optional operator-context.md next to the worker session adds a short, credential-free workstation handoff to each PC request. It is not a transcript mirror of a desktop chat.

The Railway bot alerts when the worker goes offline and reconnects. PC work requires the machine powered on, network available and a signed-in Windows session. The watchdog cannot recover from a power cut, broken network, exhausted plan allowance or a required human sign-in. Cloud monitoring and direct task reports remain independent of the PC.
